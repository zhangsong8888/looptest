## 0. 结论摘要

1. **产品定位**：本系统是"起降场侧的资源编排与协同工具"，不是空管系统、不是飞控系统。它把"起降场—起降单元—停机位"的时空资源变成可预约、可校验、可追溯的对象，并输出**建议与状态**；管制类指令仍由空中交通管理机构或其委托的航行服务提供方下达（依据：92 部第 92.525 条，见 E-01）。
2. **核心闭环**：架次创建 → 排槽（占槽）→ 起飞前确认 → 起飞（占起降单元）→ 进近 → 落地（释放起降单元、占停机位）→ 周转 → 离场（释放机位）。闭环的每一个状态跃迁都必须有"谁触发、依据什么、失败怎么办"。
3. **首版必须做对的三件事**：①槽位互斥不重复占用；②机型/起降场/时段三类准入校验；③每一次改槽、让行、取消都可追溯（审计不可缺）。
4. **最大的领域陷阱**：把"飞行计划审批状态"与"起降调度状态"合成一个状态机。MH/T 4055.2 已给出 9 个飞行计划生命周期状态（E-06），它们是**审批态**；调度需要的是另一套**执行态**。两者应通过架次关联映射，不能合并。
5. **最大的规则空白**：低空起降"时间槽"的定义、最小粒度、起降最小间隔、周转时间，在本次检索范围内**没有任何标准给出数值**（见 U-01～U-03）。因此这些必须做成**可配置参数**，并由产品负责人拍板默认值，不能由研发"按经验写死"。
6. **合规红线**：多个运行人共用同一起降场时，起降过程应接受间隔服务（92 部第 92.531 条，E-02）；提供间隔/流量管理服务需与空管机构建立协议（第 92.529 条）。本系统若未获委托，只能做"冲突提示 + 调配建议"，不得对外表述为"管制指令"。
7. **容量不是算出来的，是评估出来的**：92 部第 92.517 条明确容量取决于空域结构、服务种类与级别、天气、其他空域用户活动，应由空管机构或航行服务提供方评估（E-03）。系统只能"读取评估容量并执行"，不能自行用公式反推一个"官方容量"。
8. **首版建议范围**：单城市片区、3～5 个起降场、1 类主用机型族（多旋翼为主）、规则排槽 + 人工确认，不做 AI 自动优化、不做计费结算、不做跨省协同。

## 1. 需求规格

### 1.1 背景与问题

低空经济已进入"筑基攻坚期"，行业公认的核心痛点是"看不见、呼不到、管不住、飞不准、联不通"（E-12，IDEA 白皮书 4.0）。但在**起降场这一层**，痛点更具体、更土：

| 现状问题 | 表现 | 后果 |
| --- | --- | --- |
| 起降场信息不对称 | 飞行主体不知道附近哪个场有空位、能不能充换电、开放到几点 | 跨区域作业靠电话确认，备降预案拍脑袋 |
| 占用状态靠人喊 | 停机位/起降坪占用靠对讲机或微信群 | 同一时段两架次抢同一坪，现场冲突 |
| 计划与实况脱节 | 计划 10:00 起飞，实际 10:12，后续排班全乱 | 高峰时段排队堆积、机位周转不开 |
| 无统一口径 | 起降场状态有的叫"停航"、有的叫"临时关闭"、有的叫"维护中" | 统计报表对不上，跨系统对接反复返工 |

已有项目资料显示，同类平台对起降设施的建模已细化到"停机位占用状态（空闲/占用/维修中）、充换电桩占用数、当前排队等待数量、场地开放状态、预计最快可用时间"（E-09）；《低空智能网联系统建设导则》的起降点数据接口也已给出"起降场状态：未启用/开航/停航/故障/管制"的枚举（E-08）。**本系统的增量价值不是再建一套台账，而是把台账变成可判定的调度规则。**

### 1.2 目标用户与角色

| 角色 | 归属 | 核心诉求 | 首版权限边界 |
| --- | --- | --- | --- |
| 调度员（运行协调席） | 起降场运营方 | 一屏看全场占用、处理冲突、改槽、下发放行确认 | 可改槽、可暂停放行、可强制置"管制"状态；不可改规则参数 |
| 起降场运营管理员 | 起降场运营方 | 维护场地/机位/设备台账、开放时段、容量与状态 | 可维护本场台账；不可跨场操作 |
| 运营人（飞行主体） | 无人机运营企业 | 提交架次、查可用槽、接收改槽/延误通知、报起飞与落地 | 仅本企业架次；不可见他企成本/客户信息 |
| 飞行操作员 | 运营人 | 移动端确认起飞条件、报落地、看排队位次 | 仅本人执飞架次 |
| 监管/行业管理用户 | 监管部门 | 只读态势、容量使用、异常事件、审计追溯 | 只读 + 导出；不可改数据 |
| 系统管理员 | 平台方 | 账号、角色、参数版本、接口配置 | 不可直接改业务数据（改参数需二次确认并留痕） |

> 角色划分参照 MH/T 4055.1/4055.2 的席位设置（飞行计划席、运行协调席、飞行动态监控席等，E-07）与项目资料中的四类用户（监管方、低空运营单位、设施设备运营单位、个人与企事业单位，E-10）。**首版不实现完整 6 席位**，只落"运行协调席 + 运营人 + 监管只读"三角色族。

### 1.5 成功指标

| 指标 | 定义 | 首版目标（建议值，待确认） | 度量方式 |
| --- | --- | --- | --- |
| 排槽一次命中率 | 首次提交即获得可用槽的架次 / 总提交架次 | ≥ 85% | 演示数据集回放统计 |
| 槽位重复占用数 | 同一（起降场, 起降单元, 时刻）出现两个"已确认"预约的次数 | = 0 | 数据一致性巡检 |
| 冲突拦截率 | 构造的冲突用例中被正确拦截的比例 | 100%（0 漏判） | 20 条冲突用例集 |
| 冲突误判率 | 无冲突用例被误判为冲突的比例 | ≤ 2% | 100 条正常用例集 |
| 计划-实际偏差可观测率 | 有起飞/落地时间戳的架次 / 已完成架次 | 100% | 架次明细 |
| 落地报告完整率 | 含落地时刻、机位、异常标记的落地记录 / 应报落地架次 | 100% | 报表 |
| 关键操作审计覆盖率 | 有操作人+时间+原因+前后值的改槽/让行/取消操作 / 全部同类操作 | 100% | 审计日志抽样 |
| 平均等待时长 | 入队到获得槽的时长均值 | ≤ 8 min（演示集） | 排队明细 |

### 1.6 端到端主流程

```
[运营人] 创建架次(起降场/机型/计划时刻/任务类型)
   │
   ├─ 准入校验(R-01/R-02) ──失败──> 返回不可受理原因(可解释)
   ▼
[系统] 排槽(R-03/R-04/R-05/R-06/R-07)
   │
   ├─ 无可用槽 ──> 入队(R-08) ──> 排队/改场建议
   ▼
[运营人/调度员] 确认预约 ──> 槽状态=已确认
   ▼
[T-15min] 起飞前确认(R-11) ──失败──> 暂缓放行/重排/取消
   ▼
[运营人] 报起飞 ──> 占用起降单元(离场) ──> 在途
   ▼
[运营人] 报进近 ──> 排队/等待点提示 ──> 落地
   ▼
[系统] 释放起降单元 + 分配停机位(R-12) ──> 周转计时
   ▼
[运营人] 报离场 ──> 释放停机位 ──> 架次完成
   ▼
[系统] 统计/审计/偏差分析
```

**关键设计约束**：流程中每个"系统自动"的动作都必须可被人工否决（除纯校验类拒绝），且否决动作写入审计。

### 1.7 领域模型（数据模型）

#### 1.7.1 术语表（研发必须统一口径）

| 术语 | 定义 | 依据 |

**MovementUnit（起降单元）**：unitId、siteId、unitType（跑道/起降坪/FATO）、length/width、bearing（起降方向，主风向优选）、maxAircraftClass、status（可用/占用/维修/关闭）、bufferSeconds（起降缓冲，可继承场级默认）。

**Stand（停机位）**：standId、siteId、standType（普通/充电/换电/应急预留）、maxAircraftClass、maxTakeoffWeight、status（空闲/占用/维修中/预留）、currentAircraftId、occupiedFrom、occupiedTo。

**Sortie（架次）**：sortieId、operatorOrgId、aircraftId、aircraftType、siteId（起飞/落地可不同场）、planTakeoffAt、planLandingAt、actualTakeoffAt、actualLandingAt、taskType（应急/公共服务/载人/物流/作业/训练）、priority（P0–P4）、flightPlanId（关联审批态计划）、dispatchState（见 1.8）、cancelReason、version（乐观锁）。

**Reservation（预约）**：reservationId、sortieId、siteId、unitId、slotStart、slotEnd、usage（takeoff/landing）、state（锁定/已确认/使用中/已释放/已过期/已作废）、confirmedBy、confirmedAt。

**Occupation（占用）**：occupationId、resourceType（unit/stand）、resourceId、sortieId、startAt、endAt、source（人工/接口/自动）、releaseReason。

**QueueItem**：queueId、sortieId、siteId、priority、enqueuedAt、expectedWindow、position、state（等待/已分配/已放弃/已超时）。

**Directive（调配建议）**：directiveId、sortieId、type（改槽/等待/改场/备降）、proposedBy（system/manual）、reason、expireAt、state（待确认/已接受/已拒绝/已过期）、confirmedBy。

**AuditLog**：logId、actorId、actorRole、action、objectType、objectId、before、after、reason、occurredAt、ip。

#### 1.7.3 三条建模红线

1. **起降单元 ≠ 停机位**：起降单元按"秒级动作"占用，停机位按"分钟级周转"占用。混用会导致容量虚高。
2. **预约态 ≠ 占用态**：预约是计划权利，占用是物理事实。冲突判定必须同时看两者，但报表口径必须分开（否则"准点率"永远算不准）。
3. **审批态 ≠ 调度态**：`flightPlanId` 指向审批态（E-06 的 9 状态），`dispatchState` 是调度态。两者独立演进，只允许"审批通过"作为"可排槽"的前置条件。

### 1.8 状态机

#### 1.8.1 架次调度态（dispatchState）

| 状态 | 进入条件 | 允许迁移到 | 超时/异常处理 |
| --- | --- | --- | --- |
| 草稿 | 创建未提交 | 待排槽、已取消 | 24h 未提交自动归档（可配） |
| 待排槽 | 准入校验通过 | 已排槽、排队中、已取消 | 无槽则转排队中 |
| 排队中 | 无可用槽入队 | 已排槽、已取消、已超时 | 超时阈值触发改场建议 |
| 已排槽(待确认) | 系统分配槽成功 | 已确认、排队中、已取消 | 超时未确认释放槽（可配，建议 10 min） |
| 已确认 | 运营人/调度员确认 | 待起飞、延误、已取消 | — |
| 待起飞 | 起飞前确认通过 | 离场、延误、已中止、已取消 | 超过计划时刻 + 容差转延误 |
| 延误 | 预测/实际偏离超容差 | 已确认(改槽后)、排队中、已取消 | 触发 R-10 重排 |
| 离场 | 报起飞，占用起降单元 | 在途、异常结束 | 起飞后 N 分钟未收到在途数据告警 |
| 在途 | 收到在途位置/状态 | 进近、备降、异常结束 | 失联超阈值告警 |
| 进近 | 报进近/进入等待点 | 已落地、复飞、备降 | 等待超时转备降建议 |
| 已落地 | 报落地，释放起降单元 | 保障中、完成 | 未报落地由系统按监视数据补录（标记来源） |
| 保障中(周转) | 分配停机位 | 完成、异常结束 | 超周转时长告警 |
| 完成 | 报离场/周转结束 | —（终态） | — |
| 已取消 | 起飞前任一态取消 | —（终态） | 释放全部资源 |
| 已中止 | 起飞前被管理方中止 | —（终态） | 释放全部资源，记录中止原因 |
| 备降 | 无法在目标场落地 | 已落地、异常结束 | 记录备降场与实际落地场 |
| 异常结束 | 失联/迫降/事故 | —（终态） | 冻结关联资源，转事件调查流程 |

> 与 MH/T 4055.2 审批态的映射：`已确认→待起飞` 对应审批态"审批通过"之后的执行准备；`离场` 对应"执行"；`完成` 对应"完成"；`已取消/已中止` 对应"撤销/取消"（E-06）。**映射关系写入接口文档，不在库表合并。**

#### 1.8.2 槽状态（Slot.state）

`可用 → 锁定（预占，TTL） → 已确认 → 使用中 → 已释放`；旁支：`已过期`（锁定超时）、`已作废`（改槽/取消）。**任一时刻同一槽最多一个"已确认"或"使用中"。**

#### 1.8.3 停机位状态

`空闲 → 占用 → 空闲`；`维修中`、`预留(应急)` 为独立禁入态，可由管理员设置，设置时必须填原因与预计恢复时间。

### 1.9 调度规则（判定式）

> 每条规则均给出：判定条件（当…时）→ 应（系统行为）→ 否则（不满足时的兜底）→ 参数 → 依据/状态。
> 参数值凡未标注依据者，均为「建议值」，须由产品负责人确认后生效。

**R-01 起降场可用性准入**

- 当 架次提交时起降场 `status ∈ {未启用, 停航, 故障, 管制}`，或 计划起降时刻不落在 `openWindows` 内，**应** 拒绝受理并返回具体原因码（`SITE_CLOSED` / `SITE_FAULT` / `SITE_RESTRICTED` / `OUT_OF_WINDOW`）；**否则** 继续 R-02。
- 参数：无。依据：E-08 状态枚举 + E-11 开放时段字段。

**R-02 机型与设施适配准入**

- 当 架次机型等级 > 起降场 `maxAircraftClass`，或 > 起降单元 `maxAircraftClass`，或 机型起飞重量 > `maxTakeoffWeight`，或 起降方式与 `supportMode` 不符，**应** 拒绝并返回 `AIRCRAFT_NOT_SUPPORTED`；**否则** 进入 R-03。
- 参数：机型等级字典（微/轻/小/中/大）。依据：E-08"适配机型""支持起降方式"。

**R-03 槽粒度与对齐**

- 当 生成/接受一个预约时刻时，**应** 将 `slotStart` 向下对齐到槽粒度边界、`slotEnd = slotStart + 槽粒度`，并在返回体中同时给出"精确计划时刻"与"对齐后槽"；**否则**（时刻缺时区/缺秒精度）拒绝并返回 `INVALID_TIME`。
- 参数：`slotMinutes = 5`（建议值；备选 1 / 15，见 U-01）；时区固定 `UTC+8`。
- 依据：北京时间与 WGS84 为 MH/T 4055.2 第 5.1.7/5.1.8 条要求（E-14）；槽粒度本身无标准依据。

**R-04 槽占用互斥**

- 当 同一 `(siteId, unitId)` 上已存在状态为"已确认/使用中"的预约（**首版不区分 usage 为起飞或落地**），且新预约与其时间区间重叠，**应** 判定冲突并拒绝（`SLOT_CONFLICT`），返回冲突预约号与操作人；**否则** 创建"锁定"预约，TTL 到期未确认自动释放。
- 参数：`lockTtlMinutes = 10`（建议值）。
- 注：起飞与落地**是否可以**并行占用同一单元，取决于场地构型，首版一律不允许（保守），见 U-04；若后续选 B，则冲突键改为 `(siteId, unitId, usage)`。

**R-05 缓冲间隔判定**

- 当 同一 `(siteId, unitId)` 上，新占用区间与既有占用区间满足
  `newStart < existingEnd + bufferSeconds` **且** `newEnd + bufferSeconds > existingStart`，
  **应** 判定为间隔不足并拒绝/告警；**否则** 判定通过。
- 参数：`bufferSeconds = 60`（建议值，场级可配、单元级可覆盖）。
- 依据：92 部第 92.531 条要求共用起降场起降过程接受间隔服务（E-02）；**具体秒数无标准依据**（U-02）。

**R-06 周转间隔判定**

- 当 同一停机位上，前一架次 `actualLandingAt + turnaroundMinutes(机型, 是否充换电)` > 后一架次 `planTakeoffAt`，**应** 拒绝该机位分配并推荐次优机位；**否则** 允许分配并按区间占用。
- 参数：`turnaroundMinutes` 按机型配置；演示设定：多旋翼基础 6 min、换电 +4 min；eVTOL 基础 15 min（**演示设定值，无标准依据**，U-03）。
- 公式：`standFreeAt = actualLandingAt + turnaround + (charging ? chargingMinutes : 0)`。

**R-07 容量上限校验**

- 当 某 `(siteId, 小时窗口)` 内"已确认+使用中"的预约架次数 ≥ `assessedCapacity`，**应** 将该窗口置为"容量饱和"、拒绝新增预约并给出最近可用窗口；当使用率 ≥ `warnRatio`，**应** 仅告警不拒绝；**否则** 正常受理。
- 参数：`assessedCapacity` 必须来自评估记录（评估方/依据/日期），系统**不得**用公式反推；`warnRatio = 0.9`（建议值）。
- 依据：92 部第 92.517 条容量定义与评估要求（E-03）；业内将"容量与需求匹配"作为评估/算法问题处理，而非固定公式（E-16）。

**R-08 排队与排序**

- 当 无可用槽且运营人选择排队，**应** 创建排队项，按 `(priority 降序, enqueuedAt 升序)` 计算位次并展示预计等待；当 有槽释放，**应** 按同一排序自动分配并通知，被通知方在 `queueConfirmMinutes` 内未确认则顺延至下一位；**否则** 保持原位次并每 `refreshMinutes` 刷新预计等待。
- 参数：`queueConfirmMinutes = 5`、`refreshMinutes = 1`（建议值）。
- 注：优先级等级与是否允许"同级内插队"见 U-05。

**R-09 优先级与让行（禁止自动抢占）**

- 当 高优先级架次无可用槽，且存在低优先级"已确认"槽，**应** 生成"让行建议"（Directive）通知双方运营人与调度员，需被让行方确认或调度员双人复核后方可改槽；**否则** 不得变更既有预约，仅记录"未获让行"并保留排队。
- 参数：优先级 P0 应急/救援 > P1 医疗/警务/公共安全 > P2 载人 > P3 物流/作业 > P4 训练/测试（**建议值，无标准依据**，U-05）。
- 依据：92 部第 92.533 条流量管理方式为"飞行前修改计划 / 飞行中实时引导"（E-04），未授权系统单方剥夺已批准资源。

**R-10 延误与重排（顺延）**

- 当 `预测起飞时刻 > slotEnd + delayToleranceMinutes` 或 `实际起飞时刻 - 计划起飞时刻 > delayToleranceMinutes`，**应** 释放原槽、将架次置"延误"、按 R-08 重新排队并推送新建议；**否则** 保留原槽，仅记录偏差。
- 参数：`delayToleranceMinutes = 2`（建议值）。
- 依据：项目资料要求监控"计划起降与实际起降的偏差、起降间隔合规性、高峰时段通行能力"（E-09）。

**R-11 起飞前确认与放行**

- 当 到达 `T - preflightConfirmMinutes`，**应** 校验：①起降场/单元状态可用；②无未解除的管制/气象禁飞标记；③机位可用；④前序架次未造成单元占用冲突；全部通过则置"待起飞"并记录放行人；任一不通过则置"暂缓放行"并给出阻塞项清单；**否则**（运营人未在窗口内确认）系统**不得**自动放行，置"延误"并通知。
- 参数：`preflightConfirmMinutes = 15`（建议值）。
- 依据：MH/T 4055.2 要求系统接收起飞信息并支持起飞前资料提取（E-06）；项目资料"起飞确认"功能（E-11）。**系统不放行即不飞，但放行不等于空管许可**，UI 必须显式提示。

**R-12 落地与停机位分配**

- 当 收到落地报告（人工或监视数据补录），**应** 立即释放起降单元占用、按 `(机型适配, 充电需求, 就近原则, 周转可行性)` 分配停机位并开始周转计时；当 无可用机位，**应** 进入"等待机位"队列并触发容量告警，**不得**默认占用任一机位；**否则** 保留"已落地未分配"状态并每 `standRetryMinutes` 重试。
- 参数：`standRetryMinutes = 1`（建议值）。

**R-13 起降场状态变更联动**

- 当 起降场状态变更为 `停航/故障/管制`，**应** ①禁止新增预约；②将该场未来 `affectedWindowMinutes` 内"已确认"预约置"待重排"并通知；③对"在途/进近"架次推送备降建议（不自动改航）；**否则**（状态恢复`开航`）应解除限制并提示重排结果。
- 参数：`affectedWindowMinutes = 120`（建议值）。
- 依据：E-08 状态枚举；92 部要求流量超评估容量时提供流量管理服务（E-04）。

**R-14 人工干预与审计**

- 当 任何人对预约、占用、优先级、状态执行写操作，**应** 记录 `actorId/角色/时间/对象/前后值/原因/来源IP`，原因字段必填且不得为空白或"无"；**否则** 系统拒绝该操作（`AUDIT_REQUIRED`）。
- 依据：MH/T 4055.2 第 5.1.3 条要求日志管理（E-14）；92 部第 92.547 条要求飞行活动数据记录保存（E-15）。

**R-15 幂等与并发**

- 当 同一 `sortieId + version` 的排槽/确认请求重复到达，**应** 返回首次结果（幂等）；当 版本号落后，**应** 返回 `STALE_VERSION` 并要求刷新；**否则** 正常处理并 `version + 1`。
- 参数：`version` 乐观锁。

4. 任何"系统自动"结果必须有"来源"标记（`system` / `manual` / `interface`），报表可按来源拆分。
5. 移动端（运营人/操作员）首版只做 4 件事：查可用槽、确认/改槽、报起飞、报落地。**不做**移动端排班审批。
